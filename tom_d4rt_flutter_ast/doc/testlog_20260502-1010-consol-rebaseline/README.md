## Verdict — no wider regression

The recent interpreter / generator fixes have **not** caused a
broad regression in the component test suites. Net failure count
dropped by 9 across these seven projects. The shifts that did
happen are isolated and locally explainable:

### Improvements

- **`tom_d4rt_generator` −13 failures.** The
  `D4rtTester end-to-end dcli_scripting_guide G-DCLI-01..14`
  cluster (14 tests minus G-DCLI-09 = 13 fails on the 0429 run)
  now passes. This is the direct payoff of the bridge-generator
  work landed during the consolidation. `tom_d4rt_generator` is
  the canonical d4rt-tester project, so the same cluster
  improving in `tom_d4rt_exec` is masked by `tom_d4rt_exec`
  still having its own G-DCLI-01..14 fails (it ships its own
  copy of the suite; see *Open: cross-project G-DCLI duplication*
  below).
- **`tom_ast_generator` −1 failure.** The `(setUpAll)` failure
  in `d4rt_tester_test.dart` is gone; it has reclassified as an
  `error` on G-DCLI-12 specifically (one test → one error
  instead of one wholesale `setUpAll` blow-up). Net effect on
  this suite is one fewer red bar.
- **`tom_d4rt_ast` +31 tests, still 0 fails.** New tests were
  added during consolidation work and all pass; the historic 2
  errors in `ast_module_loader_test` (stdlib loading × 2) are
  still there and are tracked as the known starting point for
  the analyzer-free split (per the 0429 baseline note).
- **`tom_d4rt` +14 net passes** even with +4 new fails — most of
  the +19 new tests pass.

### Real regressions to triage

These three are the only items that did **not** exist on the 0429
baseline and so are the candidates for a follow-up cluster:

| Project | Test | Class | Notes |
|---|---|---|---|
| `tom_d4rt` | `GEN-056d: Extension on unknown type reports error.` | failure | Likely tied to extension-on-stdlib resolution work landed during Cluster A/B; needs targeted check. |
| `tom_d4rt` | `I-MISC-40 / I-MISC-41` (export conflict tests) | failure | Both fail in `tom_d4rt` for the first time. They have always failed in `tom_d4rt_exec` (same suite mounted twice). The fix that improved `tom_d4rt_exec` consistency may have made `tom_d4rt` start exercising the same code path. |
| `tom_d4rt` | `I-MISC-212: Incorrect return type (null for Object).` | failure | Strict-bool / strict-typing path; new fail; needs reproduction. |
| `tom_d4rt_dcli` | `VS Code Scripting API - Live Bridge Commands script can get active editor through bridge` | failure |  |
| `tom_d4rt_dcli` | `VS Code Scripting API - VSCodeWindow getActiveTextEditor returns editor info` | error |  |

The two `tom_d4rt_dcli` items are both in
`vscode_scripting_api_bridges_test.dart` and exercise the live VS
Code bridge. They almost certainly require an active VS Code
extension host; the 0429 run was performed in an environment
where the bridge was reachable, the 0502 run was not. **Treat as
environment-dependent until confirmed otherwise** — do not start
an interpreter cluster on this without first re-running the same
test against a live VS Code session.
