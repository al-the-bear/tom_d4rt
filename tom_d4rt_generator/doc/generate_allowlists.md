# Generator allowlists — what they are and how to (re)generate them

The bridge generator consults two independent **allowlists** that narrow what it
emits. They solve unrelated problems and have different lifecycles, so it is
easy to confuse them:

| Allowlist | Lives in | Authored by | Feeds | Purpose |
|-----------|----------|-------------|-------|---------|
| **Relaxer allowlist** | `doc/corpus_relaxer_allowlist.yaml` | **auto-generated** by `scan_corpus_types` | `BridgeConfig.additionalRelaxerTypes` | Cap combinatorial relaxer/RC-2 generation to the type-args a corpus actually uses. |
| **Deprecated allowlist** | per-module `deprecatedAllowlist:` in `buildkit.yaml` | **hand-authored** | `ModuleConfig.deprecatedAllowlist` | Opt one `@Deprecated` symbol back in without flooding the bridge. |

The first is the one you literally **regenerate** (it is a build artifact); the
second is a config value you **edit by hand**. This document covers both —
detailed mechanics of the deprecated allowlist live in
[deprecated_allowlist.md](deprecated_allowlist.md).

---

## 1. The relaxer allowlist — `corpus_relaxer_allowlist.yaml`

### Why it exists

For every bridged class with a single type parameter the generator emits a
`$Relaxed*<V>` wrapper (category A), and for generic instantiations it emits
combinatorial `_relax*` / `_rc2*` switch families (categories B/C). With
`generateAllRelaxers: true` these families enumerate **every** concrete bridged
class — which dominates generated size for a large surface like flutter-material.

Flipping `generateAllRelaxers: false` gates the B/C switch families down to the
union of:

```
genericExtractionSites ∪ relaxerClasses ∪ additionalRelaxerTypes
```

`additionalRelaxerTypes` is the part that must cover **type-args the scripts
write but the generator can't discover from bridge extraction sites alone**
(e.g. `ValueNotifier<MagnifierInfo>` where `MagnifierInfo` is only ever named in
a script). `corpus_relaxer_allowlist.yaml` is the committed, regenerable list of
exactly those names, scanned from a real corpus so the reduced build can't
silently drop a switch case a script exercises.

### What the list actually contains

`scan_corpus_types` walks a directory of D4rt scripts and records **every bare
type name that appears as a type argument** at any nesting depth — purely
syntactically (`parseString`, no resolution). So the entries are a mix of:

- **Flutter / dart framework types** used as generic args — `Animation`,
  `Alignment`, `AnimationController`, `AppLifecycleState`, …
- **User types declared in the corpus scripts themselves** — the demo widgets
  the test scripts define, e.g. `AnimatedAlignDemo`, `AppStateScope`,
  `AppStateDemo`.
- **Bare type-parameter identifiers** — single letters like `A`, `B` that appear
  inside `<...>` in the scripts.

`dynamic`, `void`, and `Never` are dropped (never bridge keys). Names are bare:
no nullability `?`, no import prefix, and a type's own type-args become their own
entries (`Map<String, List<Color>>` ⇒ `String`, `List`, `Color`).

The list therefore **belongs to no single package**: it is *derived from* the
flutter-material test corpus in `tom_d4rt_flutter_ast`, but the names themselves
are partly framework classes and partly the corpus scripts' own demo classes.
The YAML is correctly placed as a **generator input artifact**, not as something
owned by the flutter packages.

### The current artifact

The committed file is generated from the AST-twin corpus and carries a
provenance header:

```yaml
# Auto-generated by tom_d4rt_generator:scan_corpus_types.
# Source corpus: ../tom_d4rt_flutter_ast/test/tom_d4rt_flutter_ast_app/test/send_ast_via_http_scripts
# Files scanned: 2083, distinct type-args: 2733.
# Feeds BridgeConfig.additionalRelaxerTypes when generateAllRelaxers: false.
additionalRelaxerTypes:
  - A
  - Action
  - ...
```

### How to regenerate

Run the bundled CLI from the `tom_d4rt_generator` package root, pointing
`--corpus` at the script directory you want to scan and `--output` at the
committed artifact:

```sh
dart run tom_d4rt_generator:scan_corpus_types \
  --corpus ../tom_d4rt_flutter_ast/test/tom_d4rt_flutter_ast_app/test/send_ast_via_http_scripts \
  --output doc/corpus_relaxer_allowlist.yaml
```

CLI options (`bin/scan_corpus_types.dart`):

| Flag | Default | Meaning |
|------|---------|---------|
| `--corpus` / `-c` | *(required)* | Directory of D4rt scripts to scan (recursive, `.dart` files). |
| `--output` / `-o` | stdout | Output file. Omit to print to stdout. |
| `--format` / `-f` | `yaml` | `yaml` (the `additionalRelaxerTypes:` block, with header) or `text` (plain sorted names, for diffing/piping). |
| `--help` / `-h` | — | Usage. |

The scanner sorts and de-duplicates, so regenerating over an unchanged corpus is
deterministic and produces a byte-identical file. Read failures (not parse
failures — parsing runs in recovery mode) are reported on stderr.

### When to regenerate

Regenerate whenever the corpus grows a script that uses a **new** generic
type-argument. The static guard
`test/corpus_allowlist_reconciliation_test.dart` (`scanDirectory` over the live
corpus must be a subset of the committed allowlist) fails until the artifact is
regenerated — that is the signal. The companion test in `relaxer_reduction_test.dart`
and `corpus_type_scanner_test.dart` cover the scanner and the reduced-gating
union itself.

### Consuming the allowlist

A consumer pastes the names into a `buildkit.yaml` `d4rtgen:` section under
`additionalRelaxerTypes:` (or loads the YAML and merges it into `BridgeConfig`),
and sets `generateAllRelaxers: false`. See
[tom_d4rt_generator_configuration.md](tom_d4rt_generator_configuration.md) for
the `generateAllRelaxers` / `relaxerClasses` / `additionalRelaxerTypes` knobs.

## 2. The deprecated allowlist — `deprecatedAllowlist:`

Unlike the relaxer allowlist this one is **not generated** — there is no scanner
and no committed artifact. It is a per-module `List<String>` of simple symbol
names you author by hand in `buildkit.yaml`.

By default the generator **skips every `@Deprecated` element**
(`generateDeprecatedElements: false`) so the bridge stays aligned with the
non-deprecated API. The all-or-nothing escape hatch
(`generateDeprecatedElements: true`) floods the bridge with *every* deprecated
member. `deprecatedAllowlist` is the middle ground: opt **one** deprecated
top-level symbol back in by simple name, leaving the rest excluded.

```yaml
modules:
  - name: material
    barrelImport: package:flutter/material.dart
    outputPath: lib/src/bridges/material_bridges.b.dart
    deprecatedAllowlist:
      - RaisedButton
      - FlatButton
```

Empty (the default) ⇒ byte-identical output, fully opt-in. The match is on the
**top-level** declaration's simple name only — there is no member-level
granularity (use a `@D4rtUserBridge` override for a single deprecated method on
a live class). After editing the list, **regenerate the module's bridges**:

```sh
dart run tom_d4rt_generator:d4rtgen
```

Full mechanics — the `_isDeprecatedExcluded` decision site, the byte-identical
default guarantee, granularity limits, the `G-DEP-1..4` tests, and the deferred
both-twin regen tail — are documented in
[deprecated_allowlist.md](deprecated_allowlist.md).
