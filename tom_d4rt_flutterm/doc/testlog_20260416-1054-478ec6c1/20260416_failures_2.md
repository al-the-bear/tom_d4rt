## 2. generator_interpreter_issues_test.dart, secondary_classes_test.dart : rendering/custom_painter_semantics_test.dart (#74)

**Category:** Bridge generator — function-type param does not accept `InterpretedFunction`

### 1) Code causing the problem

Inside the demo, a custom CustomPainter subclass supplies a `semanticsBuilder`:

```dart
CustomPaint(
  painter: _MyPainter(),                // semanticsBuilder returns a list
  // OR equivalently
  foregroundPainter: _MyPainter(),
)
```

and `_MyPainter` overrides `CustomPainter.semanticsBuilder`, which has signature `List<CustomPainterSemantics> Function(Size size)?`.

The bridge for `CustomPainter` (or wherever a closure crosses the bridge) rejects the overridden getter:

```
Argument Error: Invalid parameter "semanticsBuilder":
  expected ((Size) => List<CustomPainterSemantics>)?,
  got InterpretedFunction
```

### 2) How it can be fixed

**In `tom_d4rt_generator`**: when a bridged callable parameter has a function type, the argument-adapter must detect `InterpretedFunction` and wrap it in a native Dart closure that calls the interpreted function back through the visitor. The infrastructure for function adaptation already exists for common cases (`VoidCallback`, `ValueChanged<T>`, etc.) — it needs to be extended to support the full generic signature used here.

Short-term workaround: the script can override `semanticsBuilder` by returning a static `const` list, but that neuters the demo's point.

### 3) Classification

**Generator problem** (missing function-type-parameter adaptation in bridge layer).

## Cross-cutting discovery: forward class reference in `static const`

During this analysis I traced the `_CompareRow does not have an unnamed constructor that accepts arguments` error (surfaced when running #33 after the batch-1 for-loop fix) and found a distinct, high-impact **interpreter bug** that also explains many of the framework errors seen across batches 12–22:

### Root cause

`InterpreterVisitor.visitClassDeclaration` evaluated each class's `static const` field initializers *inline* with member processing. Classes were processed in source order, so when class A had `static const _rows = [_CompareRow(...)]` and `_CompareRow` was declared *later* in source, `_CompareRow`'s constructors had not been registered yet. `findConstructor('')` returned `null` and `InterpretedClass.call` fell through to the "no unnamed constructor" branch.

### Fix applied

Split static-field evaluation out of the class-body pass:

- `InterpreterVisitor` gains a `deferStaticFieldInits` flag and a `_pendingStaticInitializers` queue plus `runDeferredStaticInitializers()` drain.
- `visitClassDeclaration` enqueues its static-field evaluation closure when the flag is set (rather than running inline).
- `d4rt_runner._executeInEnvironment` and `ast_module_loader._interpretDeclarations` now wrap the class/mixin pass with `deferStaticFieldInits = true`, then call `runDeferredStaticInitializers()` after every class has been visited.

Now every class's constructors, methods, fields, and getters are fully populated before any `static const` initializer tries to use them, regardless of source order.

### Verified impact

- `render_two_dimensional_viewport_test.dart`: the `_CompareRow` error is gone (tests now fail for an unrelated `ValueNotifier<ChildVicinity>` null-init issue — separate batch).
- `raw_radio_test.dart`: the `_PlanInfo` error is gone (same ValueNotifier issue follows).
- Expected to eliminate the identical error pattern for `_UseCase`, `_Section`, `_BootstrapStepInfo`, `_MethodInfo`, `_SubclassEntry`, `_AttachStep`, `_CompareRow`, `_PlanInfo` across the suite.

### Classification

**Interpreter problem** — fixed in this batch, spans `tom_d4rt_ast`.

## Deep-Dive #74 — Function-type parameter adaptation (`semanticsBuilder`)

### Trigger script

[test/.../rendering/custom_painter_semantics_test.dart:415-447](../../test/tom_d4rt_flutterm_app/test/send_ast_via_http_scripts/rendering/custom_painter_semantics_test.dart#L415-L447)

```dart
class _SemanticsDemoPainter extends CustomPainter {
  ...
  @override
  SemanticsBuilderCallback? get semanticsBuilder {
    return (Size size) {
      return [
        CustomPainterSemantics(rect: ..., properties: ...),
        ...
      ];
    };
  }
}
```

### Where the failure is produced

[tom_d4rt_flutterm/lib/src/bridges/flutter_proxies.b.dart:512-525](../../../lib/src/bridges/flutter_proxies.b.dart#L512-L525)

The auto-generated `D4rtCustomPainter` proxy delegates `onSemanticsBuilder` by calling the interpreted getter and then trying to coerce its return value:

```dart
onSemanticsBuilder: instance.klass.findInstanceGetter('semanticsBuilder') != null
    ? () {
  final getter = instance.klass.findInstanceGetter('semanticsBuilder');
  if (getter != null) {
    final result = getter.bind(instance).call(visitor, [], {});
    return D4.extractBridgedArg<List<CustomPainterSemantics> Function(Size)?>(
        result, 'semanticsBuilder');
  }
  ...
}
```

`getter.call(...)` returns an `InterpretedFunction` (the script's `(Size size) { ... }` closure). `extractBridgedArg<List<CustomPainterSemantics> Function(Size)?>` then tries to coerce it.

### The exact mechanism that fails

`extractBridgedArg` ([d4.dart:913-927](../../../../tom_d4rt_ast/lib/src/runtime/generator/d4.dart#L913-L927)) DOES detect `Callable + Function` types and tries to wrap via `_wrapCallableForMap<T>`:

```dart
if (unwrapped is Callable) {
  final tStr = T.toString();
  if (tStr.contains('Function')) {
    final effectiveVisitor = visitor ?? _activeVisitor;
    if (effectiveVisitor != null) {
      final wrapped = _wrapCallableForMap<T>(unwrapped, effectiveVisitor);
      if (wrapped is T) return wrapped;          // ← FAILS
    }
  }
}
```

`_wrapCallableForMap` ([d4.dart:731-801](../../../../tom_d4rt_ast/lib/src/runtime/generator/d4.dart#L731-L801)) returns either `(arg) {...}` or `() {...}` or a variadic fallback — but each is plain `dynamic Function(...)`. Two issues then conspire:

1. **Regex misses nullable function types** — `_isSingleArgFunction`'s regex `Function\(([^,)]+)\)$` requires the type string to end in `)`. The actual `T.toString()` here is `List<CustomPainterSemantics> Function(Size)?` — ends in `?`. So it matches no helper and falls through to the variadic `([p0, p1, ...]) { ... }` fallback.
2. **`is T` reified-type check fails** — Dart's reified function-type subtyping requires exact argument and return types. `dynamic Function([dynamic, dynamic, ...])` is NOT a subtype of `List<CustomPainterSemantics> Function(Size)?`. Even if (1) were fixed, the resulting `dynamic Function(dynamic)` still doesn't pass `is List<CustomPainterSemantics> Function(Size)?`.

So the wrapper falls through and the original `InterpretedFunction` is then passed through to the bridge constructor, which throws the surface error:

```
Argument Error: Invalid parameter "semanticsBuilder":
  expected ((Size) => List<CustomPainterSemantics>)?,
  got InterpretedFunction
```

### Script-level workaround

Make the interpreted closure satisfy the type by reifying it through a variable typed with the exact signature **before** passing it across the bridge:

```dart
// Doesn't work — a static const can't reference an interpreted closure,
// and a normal local cast still produces an InterpretedFunction.
```

In practice there is **no clean script-level workaround** for this case — once you return an `InterpretedFunction` through a getter that the bridge then coerces, you cannot construct a typed native closure from inside the script. Not exposing `semanticsBuilder` (returning `null` / not overriding) avoids the error but defeats the demo. Alternative: do not subclass `CustomPainter` at all, and inline the painting via `CustomPaint(painter: ...)` only with painters that don't use `semanticsBuilder`.

### Proper fix

This is a **bridge generator (`tom_d4rt_generator`) problem**:

1. **Fix the regex** in `_isSingleArgFunction` / `_isNoArgFunction` / `_isTwoArgFunction` to accept the trailing `?` for nullable function types.
2. **Generate typed wrappers per call-site**. The proxy already knows the precise signature (`List<CustomPainterSemantics> Function(Size)?`). The generator should emit a typed lambda directly:

   ```dart
   onSemanticsBuilder: () {
     final result = getter.bind(instance).call(visitor, [], {});
     if (result == null) return null;
     final callable = result as Callable;
     return (Size size) {
       final out = callable.call(visitor, [size], {});
       return D4.extractBridgedArg<List<CustomPainterSemantics>>(out, 'semanticsBuilder');
     };
   }
   ```

   Once the wrapper has the exact static type the proxy needs, the assignment compiles and runs cleanly.

3. **Same change applies to every proxy returning a typed function value** (CustomClipper, FlowDelegate, etc.) and to every constructor parameter typed `T Function(...)`.

### Classification

**Generator problem** — `tom_d4rt_generator`'s function-typed wrappers must be type-aware per call-site rather than relying on a single dynamic-typed wrapper round-tripping through `is T`.

## Deep-Dive #75 / #76 — Interpreted Widget subclass not recognized as `Widget`

### Trigger scripts

`#75`: [render_obj../relayout_when_system_fonts_change_mixin_test.dart:1238-1248](../../test/tom_d4rt_flutterm_app/test/send_ast_via_http_scripts/rendering/relayout_when_system_fonts_change_mixin_test.dart#L1238-L1248) and class def at line 1445:

```dart
class _RelayoutHostWidget extends LeafRenderObjectWidget {

Positioned.fill(
  child: _RelayoutHostWidget(...),     // ← passed across the bridge

```

`#76`: [render_absorb_pointer_test.dart:1150 + 1350](../../test/tom_d4rt_flutterm_app/test/send_ast_via_http_scripts/rendering/render_absorb_pointer_test.dart#L1350):

```dart
class _AbsorbGateHost extends SingleChildRenderObjectWidget {
  ...
}

Positioned.fill(child: _AbsorbGateHost(...))
```

### Where the failure is produced

[tom_d4rt_ast/lib/src/runtime/generator/d4.dart:1483-1510](../../../../tom_d4rt_ast/lib/src/runtime/generator/d4.dart#L1483-L1510) — `tryCreateInterfaceProxyWithVisitor`:

```dart
static T? tryCreateInterfaceProxyWithVisitor<T>(InterpretedInstance instance, ...) {
  ...
  final candidates = <String>[];
  if (klass.bridgedSuperclass != null) candidates.add(klass.bridgedSuperclass!.name);
  for (final iface in klass.bridgedInterfaces) candidates.add(iface.name);
  for (final mixin in klass.bridgedMixins)     candidates.add(mixin.name);

  for (final name in candidates) {
    final factory = _interfaceProxies[name];   // ← lookup
    if (factory != null) {
      final proxy = factory(visitor, instance);
      if (proxy is T) return proxy;
    }
  }
  return null;
}
```

For `_RelayoutHostWidget`, `klass.bridgedSuperclass.name == 'LeafRenderObjectWidget'`. For `_AbsorbGateHost`, it's `'SingleChildRenderObjectWidget'`. Neither name has a factory in `_interfaceProxies` — registered factories ([tom_d4rt_flutterm/lib/src/bridges/flutter_proxies.b.dart:454-842](../../../lib/src/bridges/flutter_proxies.b.dart#L454)) cover only `CustomPainter`, `CustomClipper`, `FlowDelegate`, `MultiChildLayoutDelegate`, `SingleChildLayoutDelegate`, `SliverPersistentHeaderDelegate`, `DataTableSource`, plus `StatelessWidget` and `StatefulWidget` registered manually in [d4rt_runtime_registrations.dart:135-157](../../../lib/src/d4rt_runtime_registrations.dart#L135-L157).

Result: `tryCreateInterfaceProxy` returns `null`, the raw `InterpretedInstance(_RelayoutHostWidget)` is passed to `Positioned.fill`'s bridge, and the bridge's argument validation rejects it — surface error:

```
Native error during bridged constructor 'fill' for class 'Positioned':
Argument Error: Invalid parameter "child": expected Widget,
got InterpretedInstance(_RelayoutHostWidget)
```

### Script-level workarounds

Because there is no proxy for `LeafRenderObjectWidget` / `SingleChildRenderObjectWidget`, the script cannot directly pass an interpreted subclass instance across a `Widget`-typed bridge boundary. Workarounds:

- **Wrap in a `Builder`**: `Positioned.fill(child: Builder(builder: (_) => _RelayoutHostWidget(...)))`. The `Builder`'s callback returns a `Widget`, and `Builder` itself is fully bridged. (The interpreted return value still has to be re-wrapped, but `Builder.builder`'s closure-coercion path goes through `extractBridgedArg<Widget>` which does call `tryCreateInterfaceProxy` — and works for `StatelessWidget` / `StatefulWidget` subclasses. So if the script's render-object widget can be re-expressed as a thin `StatelessWidget` wrapping the actual render-object work, this path succeeds.)
- **Re-architect the demo** to use a `LayoutBuilder` or `CustomPaint` for the rendering effect that the user-defined `LeafRenderObjectWidget` was demonstrating, so the script never instantiates the abstract base.

Neither workaround actually demonstrates `LeafRenderObjectWidget` / `SingleChildRenderObjectWidget` — both classes need this fix to be honestly demonstrated.

### Proper fix

Two coordinated changes:

1. **Add proxy factories** for the abstract widget base classes in `tom_d4rt_flutterm/lib/src/d4rt_runtime_registrations.dart` (or a new generated section). For each of:
   - `LeafRenderObjectWidget`
   - `SingleChildRenderObjectWidget`
   - `MultiChildRenderObjectWidget`
   - `RenderObjectWidget`
   - `ProxyWidget`
   - `InheritedWidget` / `InheritedNotifier` / `InheritedModel`

   register an `_InterpretedXxxWidget` proxy that:
   - extends the corresponding native abstract class
   - delegates `createElement`, `createRenderObject`, `updateRenderObject`, `child`, `children`, `key`, etc. to the matching interpreted methods on the wrapped `InterpretedInstance`
   - mirrors the existing `_InterpretedStatelessWidget` / `_InterpretedStatefulWidget` pattern

2. **Bridge the abstract base constructors** so that an interpreted subclass's `super(...)` call can chain through. The current bridges have empty `constructors: {}` for these classes — a generator pass should emit unnamed and `child:`-accepting constructor adapters that delegate to the proxy class's constructor.

### Classification

**Generator + interpreter problem.** Adding `LeafRenderObjectWidget` / `SingleChildRenderObjectWidget` proxies follows the same pattern as `_InterpretedStatelessWidget`. The bridge-constructor coverage requires a small generator change (do not skip `abstract` widgets when emitting unnamed constructor adapters).

[tom_d4rt_flutterm/lib/src/bridges/widgets_bridges.b.dart:32907-32919](../../../lib/src/bridges/widgets_bridges.b.dart#L32907):

```dart

  return BridgedClass(
    nativeType: $flutter_164.SingleChildRenderObjectWidget,
    name: 'SingleChildRenderObjectWidget',
```

When the interpreter executes `super(child: child)` for `_SizeReporter`, it walks up to the bridged superclass `SingleChildRenderObjectWidget` and asks for an unnamed constructor adapter. None exists — `constructors: {}` — and the runtime throws:

```

Check bridge definition.
```

### Script-level workaround

Avoid extending the abstract widget base. Instead, demonstrate the concept by:

- Subclassing `StatelessWidget` and using a normal child widget tree, or
- Using `CustomPaint` for paint-only demos.

This loses the ability to demo a custom render-object widget, but it sidesteps the bug.

### Proper fix

**Generator-side** — `tom_d4rt_generator`:

When emitting the bridge for an abstract widget base class (`SingleChildRenderObjectWidget`, `MultiChildRenderObjectWidget`, `LeafRenderObjectWidget`, `RenderObjectWidget`, `ProxyWidget`, `InheritedWidget`, etc.), generate a synthetic `''` constructor adapter that:

```dart
constructors: {

    // The interpreter is calling super({key, child}) from a subclass.
    // Return a real native instance of an "abstract base placeholder"
    // whose only role is to satisfy `super()` and the field
    // initializations on the InterpretedInstance.
    //
    // Implementation: each of these abstract bases has a private
    // proxy class registered (D4rtSingleChildRenderObjectWidget) that
    // holds the child + key from named[] and forwards
    // createElement/createRenderObject/updateRenderObject to the
    // interpreted methods. The constructor adapter creates that proxy.
    return D4rtSingleChildRenderObjectWidget(
      key: named['key'] as Key?,
      child: named['child'] as Widget,
      onCreateRenderObject: ...,
      onUpdateRenderObject: ...,
    );
  },
},
```

Combined with proxy factories from #75/#76 above, this fully enables user-defined render-object widget subclasses.

### Classification

**Generator problem** — generator must not skip constructor emission for abstract widget base classes when they have a stable proxy hook.

## Deep-Dive #79 — `EagerGestureRecognizer.new` (constructor tear-off on bridged classes)

### Trigger script

[android_view_test.dart:181-194](../../test/tom_d4rt_flutterm_app/test/send_ast_via_http_scripts/widgets/android_view_test.dart#L181):

`EagerGestureRecognizer.new` is the Dart 2.15+ **constructor tear-off** syntax — it produces a `Function` reference to the unnamed constructor.

### Where the failure is produced

[tom_d4rt_ast/lib/src/runtime/interpreter_visitor.dart:791-815](../../../../tom_d4rt_ast/lib/src/runtime/interpreter_visitor.dart#L791):

```dart
} else if (prefixValue is BridgedClass) {
  final bridgedClass = prefixValue;
  final staticGetter = bridgedClass.findStaticGetterAdapter(memberName);
  if (staticGetter != null) return wrapNativeReturnValue(staticGetter(this));

  final staticMethod = bridgedClass.findStaticMethodAdapter(memberName);
  if (staticMethod != null) return BridgedStaticMethodCallable(...);

  // No further fallback for `.new`!
  throw RuntimeD4rtException(
    "Undefined static member '$memberName' on bridged class '${bridgedClass.name}'.",
  );
}
```

For `EagerGestureRecognizer.new` the lookup is:
- Static getter `'new'` — none → null
- Static method `'new'` — none → null
- Falls through to: `Undefined static member 'new' on bridged class 'EagerGestureRecognizer'`

Compare with the `InterpretedClass` branch at [interpreter_visitor.dart:692-695](../../../../tom_d4rt_ast/lib/src/runtime/interpreter_visitor.dart#L692-L695), which DOES handle `.new`:

```dart
if (memberName == 'new') {
  final constructor = prefixValue.findConstructor('');
  if (constructor != null) return prefixValue;     // class is itself Callable
}
```

The `BridgedClass` branch is missing this clause.

### Script-level workaround

Wrap the constructor in a lambda manually:

```dart
set.add(Factory<OneSequenceGestureRecognizer>(() => EagerGestureRecognizer()));
set.add(Factory<OneSequenceGestureRecognizer>(() => VerticalDragGestureRecognizer()));
```

This is a one-line edit and fully equivalent. But `.new` syntax is idiomatic and many sample apps use it — every script that does fails until this is fixed.

### Proper fix

**Interpreter change in `tom_d4rt_ast/lib/src/runtime/interpreter_visitor.dart`** (and mirror to `tom_d4rt`). After the static-getter / static-method probes for `BridgedClass`, add:

```dart
if (memberName == 'new') {
  final ctorAdapter = bridgedClass.findConstructorAdapter('');
  if (ctorAdapter != null) {
    return BridgedConstructorTearOffCallable(bridgedClass, ctorAdapter, '');
  }
}
// And generally for named-constructor tear-offs:
final namedCtorAdapter = bridgedClass.findConstructorAdapter(memberName);
if (namedCtorAdapter != null) {
  return BridgedConstructorTearOffCallable(bridgedClass, namedCtorAdapter, memberName);
}
```

`BridgedConstructorTearOffCallable` is a small `Callable` that — when invoked — calls the constructor adapter with the supplied positional/named args and returns the resulting native instance. Mirrors the existing `_NamedConstructorTearOff` for `InterpretedClass` ([interpreter_visitor.dart:701](../../../../tom_d4rt_ast/lib/src/runtime/interpreter_visitor.dart#L701)).

### Classification

**Interpreter problem** — `.new` and named-constructor tear-off support for `BridgedClass`. This is a one-file change in each of `tom_d4rt_ast` and `tom_d4rt`, plus a tiny new `Callable` subclass.

Inside any `State<T>` subclass body, `widget` is the (typed) getter that returns the currently-bound `StatefulWidget`. It's defined on the `State<T>` base class.

### Where the failure is produced

`tom_d4rt_flutterm/lib/src/d4rt_runtime_registrations.dart:399-454` — the StatefulWidget proxy:

```dart
D4.registerInterfaceProxy('StatefulWidget', (visitor, instance) {
  ...
  return _InterpretedStatefulWidget(visitor, instance, key: key);
});

class _InterpretedStatefulWidget extends StatefulWidget {
  ...
  @override
  State<_InterpretedStatefulWidget> createState() {
    final method = _instance.klass.findInstanceMethod('createState');
    ...
    if (result is InterpretedInstance) {
      // RC-5: Check if the State subclass uses a TickerProvider mixin.
      if (_usesTickerProviderMixin(result.klass)) {
        final state = ...;
        result.nativeProxy = state;          // ← set for ticker-provider
        return state;
      }
      return _InterpretedState(_visitor, result, this);
      //                                              ↑
      //  result.nativeProxy is NOT set here — the regular State path
      //  forgets to back-link the proxy onto the InterpretedInstance.
    }
    ...
  }
}
```

When the script later runs `widget.dynamicAddressLines`, the interpreter resolves `widget` against the InterpretedInstance via [runtime_types.dart:1273-1320](../../../../tom_d4rt_ast/lib/src/runtime/runtime_types.dart#L1273-L1320):

```dart
if (currentClass.bridgedSuperclass != null) {
  final nativeTarget = bridgedSuperObject ?? nativeProxy;
  if (nativeTarget != null) {
    final bridgedSuper = currentClass.bridgedSuperclass!;
    if (name == 'widget' && bridgedSuperObject == null && nativeProxy != null) {
      try {
        final dynamic proxy = nativeProxy;
        final interpretedWidget = proxy.interpretedWidget;
        if (interpretedWidget is InterpretedInstance) return interpretedWidget;
      } catch (_) {}
    }
    final getterAdapter = bridgedSuper.findInstanceGetterAdapter(name);
    if (getterAdapter != null) return getterAdapter(visitor, nativeTarget);
    ...
  }
}
```

Because `result.nativeProxy` was never set (only the ticker-provider variants do that), `nativeTarget = bridgedSuperObject ?? nativeProxy = null`. The whole `if (nativeTarget != null)` block is skipped, lookup falls through every other branch, and finally:

```
Undefined property 'widget' on _AutofillGroupLaneState.
```

Even if `nativeProxy` were set to the `_InterpretedState` instance, the `widget` getter inherited from native `State<T>` would return the wrapper (`_InterpretedStatefulWidget`), not the script's original `_AutofillGroupLane` interpreted instance. The special-case at line 1281 expects the proxy to expose an `interpretedWidget` getter that returns the original interpreted widget — `_InterpretedState` has no such getter today.

### Script-level workaround

Capture the widget's relevant fields in `initState` via constructor parameters or via a top-level `ValueNotifier<T>` rather than reading `widget.x` from State methods. This works for static demos but is **not** a faithful demonstration of `State<T>` — the whole point of `State` is its `widget` access pattern.

```dart
// Instead of `widget.dynamicAddressLines` inside initState/didUpdateWidget,
// use:
class _AutofillGroupLane extends StatefulWidget {
  final int dynamicAddressLines;
  // expose as a top-level notifier:
  static final ValueNotifier<int> currentLines = ValueNotifier(1);
  ...
}
```

Or restructure as a `StatelessWidget` that consumes a top-level `ValueNotifier`. Both lose the `State<T>` demonstration.

### Proper fix

Two small, coordinated changes in `tom_d4rt_flutterm/lib/src/d4rt_runtime_registrations.dart`:

1. **Set `nativeProxy` for plain `_InterpretedState` too** (currently only ticker-provider variants set it):

   ```dart
   final state = _InterpretedState(_visitor, result, this);
   result.nativeProxy = state;
   return state;
   ```

2. **Store the parent widget on `_InterpretedState` and expose `interpretedWidget`** so the special-case at runtime_types.dart:1281 finds the original interpreted widget instance:

   ```dart
   class _InterpretedState extends State<_InterpretedStatefulWidget> {
     final InterpreterVisitor _visitor;
     final InterpretedInstance _stateInstance;
     final _InterpretedStatefulWidget _parentWidget;

     _InterpretedState(this._visitor, this._stateInstance, this._parentWidget);

     /// Used by runtime_types.dart's `widget` access on InterpretedInstance.
     InterpretedInstance get interpretedWidget => _parentWidget._instance;
     ...
   }
   ```

Together these two changes make `widget.dynamicAddressLines` resolve to the original interpreted `_AutofillGroupLane` instance, after which the normal property-access path returns its `dynamicAddressLines` field.

### Classification

**Bridge-runtime problem** (in `tom_d4rt_flutterm`'s State proxy), with the interpreter side already in place via `runtime_types.dart`'s special-case for `widget` + `nativeProxy.interpretedWidget`.
